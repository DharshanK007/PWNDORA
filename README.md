# NeoFactory Cyber Range — a lab layer wired directly into a real enterprise application

**Track: [Track 5] | Problem Statement: [Vulnerability Chain Exploitation Lab — Multi-Stage Web Attack Module for PWNDORA 
]**


---

## What this is

NeoFactory is a fully-featured, realistic enterprise industrial-IoT operations platform — employee records, device/asset inventory, maintenance tickets, network topology, reports — built as PWNDORA's proof of concept for a new kind of cybersecurity training lab.

The core idea: **the enterprise application itself is the lab.** There is no separate CTF-style sandbox, no isolated "exploit this fake endpoint" screen. When a learner clicks Launch on a scenario, specific real endpoints in this same application — the ones a normal employee would use every day — start exhibiting real, deliberately-planted vulnerabilities for that learner's session. The learner exploits the app by using the app: browsing Employees, reading Assets, using the search bar, logging in. A persistent status bar tracks their progress across whichever real page they're on; nothing about the pages themselves changes to signal "you're in a lab now."

Two full vulnerability chains are implemented end to end:

- **Operation Phantom Firmware** — Vulnerable Component → Broken Access Control (IDOR) → Injection → Authentication/Session flaw
- **Silent Exfiltration** — Authentication (rate-limit-free brute force) → Injection → Path Traversal → Privilege Escalation via a stolen credential

Each stage maps to a real OWASP 2021 category and MITRE ATT&CK technique, and produces a CVSS score computed from real per-stage metrics — never a hardcoded number. At the end of a run, the learner gets an auto-assembled factual draft (what happened, in what order, with what OWASP/MITRE/CVSS classification) and writes their own findings and remediation recommendations into it before submitting — the platform doesn't grade or auto-generate that analysis for them.

## Architecture overview

See `ARCHITECTURE.md` for the full diagram and data-flow documentation. In short:

- **`stage_gate.py`** is the single seam between "ordinary enterprise endpoint" and "lab-aware endpoint" — a small dependency that checks whether the requesting learner has an active scenario session whose current stage matches the endpoint being hit, and advances state on success.
- **`challenge_engine/`** validates that a specific action genuinely produced the outcome a stage expects (e.g., did the response actually contain out-of-scope data), not just that a specific input string was submitted.
- **`progress_engine/`** and **`attack_engine/`** are two deliberately separate stores fed by the same event: a personal, permanent **capability graph** per learner (what skills they've demonstrated) and a **vulnerability graph** per scenario run (the technical OWASP/MITRE/CVSS trail), which are never merged.
- **`report_generator.py`** assembles the factual half of the end-of-scenario report from real completed-stage data; the learner completes the rest through the Reports UI.

## Running it

### Option 1 — Docker Compose (recommended, single command)

```bash
docker-compose up --build
```

This launches Postgres, runs migrations, seeds the demo enterprise data (including the accounts and records both lab scenarios depend on), and starts both the backend and frontend.

- Frontend: http://localhost:3000
- Backend API: http://localhost:8001
- API docs: http://localhost:8001/docs

**Before your first real run, tear down any stale volume so you're testing what a judge will actually experience:**
```bash
docker-compose down -v
docker-compose up --build
```

### Option 2 — manual / local dev

```bash
# Backend
cd backend
pip install -r requirements.txt
alembic upgrade head
python -m app.seed.seed
uvicorn app.main:app --reload

# Frontend (separate terminal)
cd frontend
npm install
npm run dev
```

## Judge test instructions

1. Log in at `http://localhost:3000/login` with the seeded admin account (see seed output/logs for the generated credentials, or check `backend/app/seed/seed.py` for the seeded account list).
2. Browse the app normally — Employees, Assets, Network, Maintenance — to see the underlying enterprise product this lab is built on top of.
3. Navigate to **Cyber Range → Scenarios**, open **"Operation Phantom Firmware,"** read the brief, click **Launch**. Note that you are *not* redirected to a separate screen — you land back in the normal app, with a status bar now visible at the top.
4. Play through the four stages using the real Assets, Employees, and Search pages, and the real login/session flow — the scenario's discovery-process text in the mission briefing describes what to investigate at each stage.
5. On completion, go to **Reports**, open the auto-generated draft, and fill in the Analysis/Recommendation fields to see the learner-authored half of the report flow.
6. Repeat with **"Silent Exfiltration"** to see the second chain (Authentication → Injection → Path Traversal → Privilege Escalation).

## Known limitations (as of this submission)

Being upfront about the current state matters more than presenting a polished facade a judge might discover is wrong live. As of this submission:

- **Session scoping needs verification.** Scenario state resolution should be scoped per authenticated learner. If two judges test simultaneously against the same running instance, confirm this doesn't cause session cross-talk before relying on concurrent testing.
- **The injection stage (both scenarios) is a simplified simulation** of an unsanitized search query rather than a full parameterized-query engine against live data — it demonstrates the concept and the OWASP/MITRE mapping faithfully, but a security researcher inspecting the implementation closely will find it's pattern-based rather than a genuine query-construction flaw.
- **Dual routing** (a stage being reachable via more than one valid exploit path) is specified in the scenario schema but not yet exercised by either shipped scenario.
- **The `credentials_to_use` field** shown in the mission briefing is closer to a worked hint than a pure discovery challenge for some stages — a design tradeoff made for demo reliability under time pressure, and a clear next-iteration target (see `PWNDORA_INTEGRATION.md`).
- Only two scenarios exist; there is no in-product scenario-authoring tool yet — new scenarios are hand-authored YAML plus the corresponding endpoint modification.

## What's next (post-hackathon roadmap, if useful context for judges)

- Generalize `challenge_engine`'s transition-check logic away from per-scenario hardcoded branches toward a declarative, reusable check-type vocabulary in the YAML schema, so new scenarios require no new backend code.
- Build a real reusable vulnerability-node library (the "vulnerability graph" as a shared, author-facing map) that a scenario designer can compose new chains from instead of writing bespoke Python per scenario.
- AI mentor/hint layer (`ai-service/`) — scaffolded, not yet implemented.
